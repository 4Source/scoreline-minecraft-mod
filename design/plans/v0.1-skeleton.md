# Scoreline v0.1 Skeleton – Implementation Plan

Nov 11, 2026 · @Dennis

**Goal:** an empty Scoreline mod that loads on NeoForge 26.3, with tests, a coverage gate and a release flow in place, so every later step only adds features.

**Approach:** the project is generated from the MultiLoader Template and reduced to a `common` and a `neoforge` module. One small piece of real logic, `RequestBudget`, is built test-first so that the test setup and the coverage gate have something to measure. Two GitHub workflows build and test every change and publish releases to GitHub.

**Tech stack:** Java 25, Gradle (the template's wrapper), NeoForge for Minecraft 26.3 with ModDevGradle, JUnit 5, JaCoCo, GitHub Actions, git-cliff.

**Spec:** `design/spec.md` in the repository (the Scoreline design spec).

**Working method:** the tasks are done in order, one pull request per task; steps are ticked off as they are done. The plan names files, interfaces, exact values and test cases; the code itself is written by the implementer. Steps marked **Check first** depend on a tool's current behaviour and are confirmed before relying on them. If a check fails, the plan is adjusted before continuing.

**Two agreed deviations from the spec:**

- `RequestBudget` belongs to v0.2 (the request budget per player). It is pulled into v0.1 because an empty mod has no logic to test, and the coverage gate would measure nothing.
- The `fabric` module is removed now and re-created from the then-current template in v0.9, instead of being kept as a stub that must be updated with every Minecraft version.

Gradle is not installed separately: the project carries its own launcher, `gradlew`. Every build, test and run step in this plan is a Gradle command in a terminal, so the steps do not depend on the editor.

**Gradle commands used in this plan**

| Command | What it does |
| --- | --- |
| `./gradlew build` | Compiles all modules, runs the unit tests and all checks, and packages the jar |
| `./gradlew :common:test` | Runs only the unit tests of the `common` module |
| `./gradlew :common:check` | Runs the tests and every verification of `common`, including the coverage gate |
| `./gradlew :neoforge:runClient` | Starts a test copy of Minecraft with the mod |
| `./gradlew :neoforge:runGameTestServer` | Starts a server without a window, runs the registered game tests and stops |

A name such as `:common:test` means the task `test` in the module `common`. The first Gradle run downloads and prepares Minecraft, which can take ten minutes or more.

**Terms**

| Term | Meaning |
| --- | --- |
| Mod loader (NeoForge) | The program that starts Minecraft and loads mods into it. A mod jar is built for one loader |
| `common` module | Code shared by all loaders. It knows Minecraft, but nothing about NeoForge |
| `neoforge` module | The small part that plugs `common` into NeoForge |
| `build-logic` | Shared Gradle build rules of the template, applied to every module |
| Mod metadata | A file inside the jar (`neoforge.mods.toml`) with the mod's ID, name and version. The build fills it from `gradle.properties` |
| Run | A ready-made way to start Minecraft with the mod, declared in `neoforge/build.gradle` and started as a Gradle task |
| Mixin | A hook that changes Minecraft's own code. Not used in v0.1; the TAB overlay in v0.3 is the first |

**Rules**

- `common` contains no NeoForge code; `neoforge` contains no logic, only registration.
- Logic that needs no Minecraft classes is kept free of them so it can be unit tested.
- Coverage gate on logic code: at least 95% of lines and 90% of branches.
- Commits follow the conventional format (`feat:`, `fix:`, `chore:`, `test:`, `docs:`, `ci:`, `build:`), because the changelog is generated from them.
- `master` is protected: changes arrive by pull request and the build workflow must pass.
- Workflow actions are referenced by major-version tag; no Dependabot.
- Bot pull requests are opened with the GitHub App token.

## Review focus

The five cases most likely to go wrong unnoticed. Each has a test in the task that owns it.

1. **T-06:** a player's budget is refilled after 2.5 intervals. A reasonable person expects the half interval to count towards the next token, not to vanish.
2. **T-07:** the server clock jumps backwards. Expected: no exception, no free tokens, refilling continues from the latest time seen.
3. **T-10:** the coverage gate measures no classes at all, for example after a package is renamed. Expected: the build fails instead of passing with nothing measured.
4. **T-11:** the smoke run passes although the mod was not loaded, for example because of broken metadata. Expected: the run fails unless the log shows Scoreline's start line.
5. **T-13:** the release workflow is started while the computed version's tag or release branch already exists, for example after a run that failed halfway. Expected: it stops before creating a branch, commit or pull request.

## Test design

`CAP` = 3 tokens and `T` = 1,000 ms in all `RequestBudget` tests.

| ID | Unit / flow | Technique | Case → expected | Bug it catches | Level | Prio | Task |
| --- | --- | --- | --- | --- | --- | --- | --- |
| T-01 | RequestBudget | Starter | new budget, request at 0 → allowed | budget starts empty | Unit | P1 | 3 |
| T-02 | RequestBudget | Boundary | `CAP` requests at 0 → allowed; request `CAP + 1` → refused | off-by-one in the capacity check | Unit | P1 | 3 |
| T-03 | RequestBudget | State transition | drained at 0; at `T` → one allowed, the next refused | no refill, or refill of more than one token | Unit | P1 | 3 |
| T-04 | RequestBudget | Boundary | drained at 0; at `T - 1` → refused | refill rounds up | Unit | P2 | 3 |
| T-05 | RequestBudget | Boundary | drained at 0; at `100 * T` → `CAP` allowed, then refused | tokens pile up beyond the capacity | Unit | P1 | 3 |
| T-06 | RequestBudget | State transition | drained at 0; at `2 * T + T / 2` → two allowed, third refused; at `3 * T` → allowed | leftover time dropped at refill | Unit | P2 | 3 |
| T-07 | RequestBudget | Error guessing | drained at `5 * T`; at `4 * T` → refused, no exception; at `6 * T` → one allowed, the next refused (assumed) | negative elapsed time adds or removes tokens, or throws | Unit | P2 | 3 |
| T-08 | RequestBudget | Equivalence partitioning | capacity 0 or -1, or interval 0 or -5 → `IllegalArgumentException` | zero interval divides by zero; zero capacity never allows a request | Unit | P3 | 3 |
| T-09 | Coverage gate | Decision table | one `RequestBudget` test removed → `check` fails with a coverage message | gate not wired into the build | Build | P1 | 4 |
| T-10 | Coverage gate | Error guessing | logic package list matches no class → `check` fails | gate passes while measuring nothing | Build | P1 | 4 |
| T-11 | Smoke run | Integration failure | server starts with the mod and stops by itself → exit code 0 and the log contains `Scoreline 0.1.0 loaded` | mod missing from the game; crash at start | Integration | P1 | 5 |
| T-12 | Release flow | Starter | `no tag → 0.1.0; with tag v0.1.0: patch → 0.1.1, minor → 0.2.0, major → 1.0.0; with v0.9.0 and v0.10.0: minor → 0.11.0; a dry run creates nothing` | wrong bump arithmetic; tags sorted as text; dry run has side effects | Workflow | P1 | 7 |
| T-13 | Release flow | Error guessing | tag or release branch of the computed version already exists → stops before any branch, commit or pull request | half-finished duplicate release | Workflow | P1 | 7 |
| T-14 | Release flow | Integration failure | tag does not equal the version in `gradle.properties` on the merge commit → run fails before building | jar and tag disagree | Workflow | P1 | 7 |

T-07's expected behaviour is not stated in the spec; it is what a reasonable admin would expect, and is marked as assumed.

## Task 3: Unit tests and the first logic unit, `RequestBudget`

`RequestBudget` limits how often one player's requests are answered: a player may send a short burst, then one request per interval. It is plain Java with no Minecraft classes, built test-first.

**Files**

- Modify: `common/build.gradle` (JUnit 5 as test dependency, tests run on the JUnit platform)
- Create: `common/src/main/java/io/github/foursource/scoreline/net/RequestBudget.java`
- Test: `common/src/test/java/io/github/foursource/scoreline/net/RequestBudgetTest.java`

**Interfaces**

- Produces: `public final class RequestBudget` with
  - `public RequestBudget(int capacity, long refillIntervalMillis)`: starts full; throws `IllegalArgumentException` if either value is below 1
  - `public boolean tryAcquire(long nowMillis)`: takes one token if one is available and returns whether it did
- Rules: one token returns per full interval, never more than `capacity`; time left over after a refill counts towards the next token; a `nowMillis` earlier than the latest one seen is treated as no time passed.
- The current time is passed in, never read from the system clock, so tests are exact and repeatable.

* [ ] **Step 1: Add JUnit 5 to `common/build.gradle`** and confirm an empty test run works.

Run: `./gradlew :common:test` Expected: `BUILD SUCCESSFUL`

- [ ] **Step 2: Implement tests T-01 to T-08 from the Test design table, one at a time and in that order:** write the test, run it and see it fail, write just enough of `RequestBudget` to pass, run it and see it pass. Each test method carries its ID in its name (for example `t03_oneTokenReturnsAfterOneInterval`) and a one-line comment naming the bug it catches. "Drained at t" in the table means `CAP` successful requests at time t. T-08 is one parametrized test with four cases.
- [ ] **Step 3: Run the whole test class.**

Run: `./gradlew :common:test` Expected: 11 tests passed (seven single tests and the four cases of T-08), 0 failed

## Task 7: Release flow up to GitHub Releases

A release is started by hand with a patch, minor or major choice and ends as a draft GitHub Release with the jar attached. Store uploads are added in v0.3.

The version arithmetic and the version check live in two small scripts, so they can be tested locally; the workflow only calls them.

**Files**

- Create: `scripts/next-version.sh`, `scripts/check-version.sh`
- Create: `cliff.toml`, `CHANGELOG.md`
- Create: `.github/workflows/release.yml`

**Interfaces**

- Consumes: secrets `APP_ID` and `APP_PRIVATE_KEY` (Task 1); the `build` check and auto-merge (Task 6); `./gradlew build` and `scripts/smoke.sh`.
- Produces: `scripts/next-version.sh <patch|minor|major>` prints the next version without a leading `v`. With no `v*` tag it prints the version from `gradle.properties` unchanged. Otherwise it takes the highest `v*` tag and applies the bump. It exits with code 1 and a usage line for any other argument, and with code 1 and `Release vX.Y.Z already exists or is in progress` if the tag `vX.Y.Z` or the branch `release/vX.Y.Z` exists locally or on `origin`.
- Produces: `scripts/check-version.sh <version>` exits with code 0 if `gradle.properties` contains `version=<version>`, else with code 1 and `Version mismatch: expected <version>, found <actual>`.

* [ ] **Step 1: Write `scripts/next-version.sh` and test it locally (T-12, T-13).** Use throwaway tags and branches, and delete them afterwards.

| Tag `v0.1.0` | `scripts/next-version.sh patch` | `0.1.1` | 0 |

| Job | What it does |
| --- | --- |
| `version` | Checks out with full history and all tags, runs `scripts/next-version.sh` with the chosen bump, and passes the result on. In a dry run it writes the version and the changelog section to the job summary, and all later jobs are skipped |

| `draft` | Creates a draft GitHub Release for the tag with this version's changelog section as its text and the jar attached; marked as a pre-release while the version is below 1.0.0 |
